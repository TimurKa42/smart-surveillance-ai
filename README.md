Це окремий застосунок від десктопної версії (`../main.py` на
CustomTkinter). CustomTkinter/Tkinter не працює на Android і не
збирається в APK взагалі — тому весь інтерфейс тут переписаний на
Kivy. Логіка нарізки відео (`video_tools.py`) взята з десктопної
версії, а звернення до Gemini (`gemini_tools.py`) — переписане з нуля
під REST API (деталі нижче).

## Що робить застосунок

1. **Екран Setup** — при першому запуску просить встав API-ключ Gemini.
   Знизу — посилання "Немає ключа? Дізнатись, як отримати", яке
   відкриває https://aistudio.google.com/apikey в браузері. Ключ
   зберігається у `.env` в теці даних застосунку (не поруч з кодом,
   бо APK — це архів лише для читання) через `config.py` і більше не
   питається при наступних запусках.
2. **Екран Main** — вибір відео (нативний пікер галереї на Android /
   `plyer` для десктоп-тесту), текстовий запит (до 200 символів),
   вибір моделі аналізу (**3.5 Flash-Lite** — швидше, **3.6 Flash** —
   точніше), кнопка «Почати аналіз», статус прогресу по кроках
   (нарізка кадрів → запит до Gemini → збереження знахідок), звіт зі
   скріншотами знайдених моментів.
3. **Меню (попап налаштувань)** — перемикач теми (Авто / Світла /
   Темна), перемикач мови (UA / EN), увімкнення вібрації та повзунок
   її сили (з тестовим імпульсом одразу під час перетягування),
   перегляд історії всіх кадрів з попередніх аналізів, скидання
   API-ключа.
4. **Історія кадрів** — окремий попап зі списком усіх знайдених
   моментів за весь час (дата/час), відкриття кожного в повноекранному
   переглядачі (lightbox) із можливістю зберегти в галерею або
   видалити, масове видалення вибраних записів.

Усі текстові рядки інтерфейсу — на двох мовах (`localization.py`),
включно з повідомленнями про помилки (нема інтернету, невірний
API-ключ, ліміт запитів, тимчасова недоступність Gemini тощо) —
Gemini API повертає технічну помилку, а `gemini_tools.py` класифікує
її (`GeminiApiError.kind`) і UI показує зрозумілий людині текст замість
сирого виключення.

Усі налаштування (тема, мова, стан і сила вібрації) зберігаються між
запусками через `settings_store.py` (`settings.json` у теці даних
застосунку).

Орієнтація екрана зафіксована на **portrait** (`buildozer.spec`) —
альбомний режим свідомо вимкнено, бо для утилітарного сценарію
"вибрав відео → отримав звіт" він не додає користі, а лише подвоює
обсяг верстки, яку треба підтримувати.

## Технологічний стек

- **UI:** [Kivy](https://kivy.org/) (`.kv`-розмітка в `smartsurveillance.kv`)
- **Комп'ютерний зір:** OpenCV (нарізка кадрів, детекція руху)
- **AI-аналіз:** Gemini REST API (`gemini-3.5-flash-lite` / `gemini-3.6-flash`) напряму через `requests`
- **Мережа/системні виклики на Android:** `pyjnius`, `plyer`
- **Мінімальна версія Android:** API 24 (Android 7.0), збирається під `arm64-v8a`
- **Python:** 3.x (сумісний з python-for-android; повний список залежностей — у `requirements` файлу `buildozer.spec`)

## Чому REST API замість офіційного google-genai SDK

Офіційна бібліотека `google-genai` всередині залежить від `pydantic`,
а той — від `pydantic_core`, скомпільованого Rust-модуля.
python-for-android не вміє коректно зібрати такі модулі під
архітектуру телефону (ARM64) і завжди підставляв версію під
архітектуру сервера збірки (x86_64), через що застосунок падав з
`is for EM_X86_64 instead of EM_AARCH64` одразу при старті. Тому
`gemini_tools.py` робить прямі HTTP-запити через `requests` (чистий
Python, без скомпільованих залежностей) до Gemini REST API — трохи
більше ручної роботи з формуванням JSON, зате без проблем з
архітектурою.

## Чому кадри більше не перевертаються на 90°

На Android-збірці OpenCV (`CAP_PROP_ORIENTATION_META`) завжди повертав
`0`, хоча відео, зняте телефоном у вертикальному положенні, насправді
містить прапорець повороту в метаданих контейнера — просто десктопна
збірка OpenCV вміє його читати, а Buildozer-збірка під Android ні.
Через це кадри з таких відео виходили "лежачими" на 90°.

Рішення — власний, чистопитонівський парсер бінарної структури MP4 у
`video_tools.py`: він читає безпосередньо атом `tkhd` (track header) з
контейнера й дістає звідти матрицю повороту, не покладаючись на
підтримку цього прапорця в OpenCV. Це прибирає залежність від
конкретної збірки OpenCV і працює однаково на десктопі й на Android.

## Структура проєкту

| Файл | Призначення |
|---|---|
| `.github/workflows/build-apk.yml` | GitHub Actions: автоматична збірка APK у хмарі (без локального Linux), артефакт `smart-surveillance-apk`. |
| `buildozer.spec` | Конфігурація збірки APK: назва, пакет, залежності, дозволи Android, `orientation = portrait`. |
| `config.py` | Безпечне збереження/завантаження API-ключа Gemini (`.env` у теці даних застосунку). |
| `gemini_tools.py` | REST-звернення до Gemini: паралельний аналіз пачок кадрів, класифікація помилок мережі/API. |
| `localization.py` | Словник рядків UA/EN, включно з текстами помилок. |
| `main.py` | Точка входу, екрани, ScreenManager, уся бізнес-логіка UI. |
| `settings_store.py` | Збереження/завантаження налаштувань (`settings.json`): тема, мова, вібрація. |
| `smartsurveillance.kv` | Уся візуальна розмітка: стилі, кастомні кнопки, екрани, попапи. |
| `theme.py` | Палітри світлої/темної теми + визначення системної теми Android (режим "Авто"). |
| `video_tools.py` | Нарізка кадрів через OpenCV, детекція руху, власний MP4-парсер орієнтації (атом `tkhd`), збереження скріншотів. |

## ВАЖЛИВО: APK не можна зібрати "просто скриптом" на своєму комп'ютері без підготовки

Компіляція APK вимагає завантаження Android SDK/NDK (кілька гігабайт)
і працює лише через **buildozer на Linux** (macOS частково, Windows —
тільки через WSL). Якщо немає бажання ставити все це локально —
у репозиторії вже налаштований workflow **GitHub Actions**
(`.github/workflows/build-apk.yml`), який збирає APK у хмарі без
власної Linux-машини (спосіб 2 нижче). Весь код і конфігурація
(`buildozer.spec`) вже готові — залишається обрати спосіб і запустити
збірку.

## Вимоги

- **Для способу 1 (локально):** Linux (Ubuntu/Debian) або WSL на
  Windows; на macOS збірка можлива частково. Python 3.10+ та `pip`.
- **Для способу 2 (GitHub Actions):** нічого локально ставити не
  треба — тільки доступ до репозиторію на GitHub.
- Android-телефон з увімкненою "Налагодженням USB" (для тестування на
  пристрої, в обох способах).
- Ключ Gemini API — отримати можна на https://aistudio.google.com/apikey.

## Як зібрати APK самому

Є два способи. Спосіб 1 — повністю локально (потрібен Linux/WSL).
Спосіб 2 — збірка в хмарі через GitHub Actions, без своєї Linux-машини
взагалі.

### Спосіб 1: Локально на Linux

#### 1. Підготовка (один раз)

На Ubuntu/WSL:
```bash
sudo apt update
sudo apt install -y python3-pip build-essential git python3-dev \
    ffmpeg libsdl2-dev libsdl2-image-dev libsdl2-mixer-dev libsdl2-ttf-dev \
    libportmidi-dev libswscale-dev libavformat-dev libavcodec-dev zlib1g-dev

pip install --user buildozer cython
```

#### 2. Тест на комп'ютері (без Android, швидка перевірка інтерфейсу)

```bash
cd mobile
pip install kivy plyer requests python-dotenv opencv-python pillow
python main.py
```

Так можна одразу побачити екран вводу ключа і основний екран, не
чекаючи довгої збірки APK. (Бібліотеки `google-genai`/`pydantic` більше
не потрібні — див. розділ вище.)

#### 3. Збірка APK

```bash
cd mobile
buildozer android debug
```

Перша збірка займе **30-60+ хвилин** (buildozer сам завантажує Android
SDK/NDK і компілює всі залежності, включно з opencv — саме він
найдовше збирається). Готовий файл з'явиться в `mobile/bin/*.apk`.

#### 4. Встановлення на телефон для тесту

```bash
buildozer android deploy run logcat
```
(телефон має бути підключений по USB з увімкненою "Налагодження USB").

### Спосіб 2: Через GitHub Actions (без власного Linux)

Збірку можна повністю перекласти на GitHub — не потрібно нічого
встановлювати локально, все відбувається на хмарному раннері
(`ubuntu-22.04`). Workflow вже лежить у репозиторії:
`.github/workflows/build-apk.yml`.

1. Відкрий репозиторій на GitHub → вкладка **Actions**.
2. Обери workflow **"Build Android APK"** зі списку зліва.
3. Натисни **Run workflow** (запуск вручну, `workflow_dispatch`) —
   збірка також запускається автоматично при будь-якому push зі
   змінами в теці `mobile/**`.
4. Дочекайся завершення (кольоровий індикатор стане зеленим ✅) —
   збірка триває приблизно стільки ж, скільки й локальна перша
   збірка.
5. Відкрий завершений запуск → розділ **Artifacts** внизу сторінки →
   завантаж **smart-surveillance-apk** (це zip з готовим `.apk`
   всередині).

Що саме робить workflow: ставить Python 3.11 та системні залежності
(включно з `openjdk-17-jdk`), встановлює Buildozer + Cython, виставляє
`JAVA_HOME` на JDK 17 (без цього кроку buildozer намагається зібрати
проти неправильної версії Java), збирає `buildozer -v android debug`
(автопідтвердження ліцензій Android SDK через `yes |`) і завантажує
готовий `.apk` як артефакт.

Мінус способу: на безкоштовному GitHub-тарифі раннер не зберігає кеш
Android SDK/NDK між запусками (якщо не налаштовано окремо) — тому
кожна збірка фактично "перша" за часом, на відміну від локальної
машини, де повторні збірки набагато швидші.

## Що варто знати перед захистом проєкту

- **opencv на Android** — важка залежність, перша збірка довга і може
  вимагати донастройки версій (`android.ndk`, `android.api` в
  `buildozer.spec`) залежно від версії buildozer. Якщо збірка падає на
  кроці opencv — це найчастіша причина проблем з мобільними Kivy+CV
  проєктами взагалі, не специфічна для цього коду.
- API-ключ Gemini зберігається лише локально на пристрої (`.env` у
  теці даних застосунку) і ніколи нікуди не передається, окрім прямих
  запитів до Google Gemini.
- Мобільна й десктопна версії — окремі кодові бази з різним UI-шаром,
  але спільною логікою нарізки відео; зміни у форматі кадрів
  (`video_tools.py`) варто синхронізувати в обох місцях вручну.
